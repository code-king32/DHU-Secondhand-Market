# 商品与线下交易接口

商品与交易模块支持登录后的发布、检索、申请及线下交易完成。金额为人民币，保留最多两位小数，范围为 0 至 1000000。业务接口返回 JSON，图片读取返回图片内容；错误使用 HTTP 状态码和 `message` 字段。

写操作要求已认证、正常状态的登录 Session。角色与用户编号由 Session 和数据库确定，请求体不能自行指定买家或卖家编号。所有商品及交易操作都会检查所属关系。

## 商品接口

| 方法与路径 | 用途 |
|---|---|
| POST /api/goods | 发布商品，返回 201 |
| PUT /api/goods/{id} | 编辑本人待售或已下架商品 |
| POST /api/goods/{id}/shelf | 上下架，JSON 为 `{"onSale":true}` 或 false |
| GET /api/goods | 公开检索在售商品 |
| GET /api/goods/{id} | 商品详情，已下架商品返回 404 |
| GET /api/goods/mine | 本人商品，包括已下架、交易中、已售 |
| GET /api/goods/{id}/management | 本人商品管理详情 |

发布、编辑的请求体示例：

```json
{
  "title": "线性代数教材",
  "description": "八成新，校园内当面交易",
  "price": 20.00,
  "category": "TEXTBOOK",
  "imageUrls": ["https://example.invalid/book.png"]
}
```

标题最多 100 字符，描述最多 5000 字符。分类支持 `TEXTBOOK`、`ELECTRONICS`、`DAILY`、`CLOTHING`、`OTHER`，未填时使用 OTHER。图片最多九张，`imageUrls` 可使用上传接口返回的 `/api/images/{name}`，也兼容原有有效 HTTP/HTTPS 图片地址；服务端不抓取远程图片。

### 图片上传与读取

- `POST /api/images`：要求已认证且正常的登录 Session，以 `multipart/form-data` 上传单个 `file` 字段。成功返回 201 和 `{"url":"/api/images/32位随机文件名.png"}`。前端将返回地址加入商品的 `imageUrls`，不需要用户填写 URL。
- `GET /api/images/{name}`：公开读取已上传图片，返回 `image/png` 或 `image/jpeg`；不存在或非法文件名返回 404。
- 只接受能解码的 JPG、PNG，单文件不超过 5 MB，分辨率不超过 2000 万像素。服务端按真实格式校验并重新编码，忽略原文件名；非法图片返回 400，超限返回 413。上传写请求仍受来源检查保护，其他业务接口仍只允许 JSON。
- 默认保存位置为后端启动目录下的 `uploads/images/`，可通过 `app.images.directory` 配置，目录已被 Git 忽略。数据库记录所有者、实际存储大小、闲置时间及商品引用，站内图片只能由上传者用于发布和编辑；商品与图片引用在同一事务中提交。
- `/api/images/` 为站内图片保留路径。完整 HTTP/HTTPS 地址中的该路径（含编码、路径参数及可规范化的路径片段）在保存前统一转为 `/api/images/{name}`，执行相同的所有者校验和引用登记，不能通过更换域名或添加查询参数绕过检查；响应和数据库均保存规范路径。其他路径的合法外部图片地址保持原样，服务端不发起网络请求。已有商品编辑保存时也会补登记其完整站内图片地址的引用。
- 默认每人最多100张、总量100 MB，超出返回409。移除图片或取消发布后，未被引用的文件闲置满24小时才会清理，后台每小时检查，启动后第一次检查延迟60秒。仍被任意商品引用的文件不会被删除；清理和发布按相同锁顺序串行，删除失败会保留标记以便重试。配置项为 `app.images.max-per-user`、`app.images.max-bytes-per-user`、`app.images.unused-retention-hours`、`app.images.cleanup-delay-ms`。
- 升级前未记录归属的文件不会被自动扫描删除；编辑已有商品时可接管该商品原有站内图片，未知文件不会被任意用户认领。旧外部HTTP/HTTPS图片继续兼容，不计入本地文件配额。

公开检索支持 `keyword`、`category`、`page`、`size`。`page` 默认 1，范围 1 至 100000；`size` 默认 20，范围 1 至 100。关键词对标题、描述进行不区分大小写的字面匹配，百分号及下划线按普通字符处理。教材专区使用 `category=TEXTBOOK`。分页响应为 `{ "items": [], "total": 0, "page": 1, "size": 20 }`。

商品响应包含 `id`、`sellerId`、`title`、`description`、`price`、`category`、`imageUrls`、`status`、`createdAt`、`updatedAt`。状态分别为 `ON_SALE` 在售、`TRADING` 交易中、`SOLD` 已售、`OFF_SHELF` 已下架、`HIDDEN` 管理员隐藏。隐藏商品的公开详情返回 404，所有者不能自行编辑或重新上架，以防撤销治理处置。

公开列表及其总数只包含账号正常且邮箱已认证的卖家商品；卖家被禁用、注销或未认证时，公开详情也返回 404。禁用不改变商品原有状态，恢复账号后符合条件的商品重新可见。

## 交易接口

| 方法与路径 | 用途 |
|---|---|
| POST /api/trades | 发起申请，请求为 `{"goodsId":1}`，返回 201 |
| GET /api/trades | 本人的交易，支持 role=ALL/BUYER/SELLER 和分页 |
| GET /api/trades/{id} | 买卖双方查看交易详情 |
| POST /api/trades/{id}/accept | 卖家接受申请 |
| POST /api/trades/{id}/confirm | 当前一方确认线下交易完成 |
| POST /api/trades/{id}/cancel | 买家或卖家取消未完成交易 |

动作接口无需请求体，也可发送空 JSON。交易响应包含 `id`、`goodsId`、`sellerId`、`buyerId`、`agreedPrice`、`status`、`buyerConfirmed`、`sellerConfirmed`、`createdAt`、`updatedAt`。`agreedPrice` 为买家发起申请时的价格快照，之后编辑商品不会更改旧申请的金额。

## 状态与权限

多个买家可以对同一在售商品分别申请，状态为 PENDING。同一个买家对同一商品只能保留一笔 PENDING 或 ACCEPTED 交易，取消后可重新申请。不能购买自己的商品。

卖家接受其中一笔申请后，该交易为 ACCEPTED，商品进入 TRADING，其他申请保留 PENDING。完成需要买家、卖家各确认一次；双方都确认后交易为 COMPLETED，商品为 SOLD，其余 PENDING 申请自动取消。重复确认已经完成的交易返回当前状态。

取消 ACCEPTED 交易会恢复商品为 ON_SALE，卖家可以处理其他申请。已完成交易不能取消。交易中及已售商品不能编辑或上下架。非交易双方不能读取或操作交易。商品所有者不能通过编辑或请求体变更所属人。

账号注销时，进行中的 ACCEPTED 交易会阻止注销。允许注销后，在售商品会下架，该用户参与的 PENDING 申请会取消。申请、接受等事务在数据库中按用户编号顺序锁定买卖双方账号，核验实时状态后再锁商品、交易，与注销事务串行协调。

## 本轮实现选择

以下细节为当前实现，仍待团队确认：卖家接受一笔申请即锁定商品；TRADING 时拒绝新的申请；取消被接受交易恢复在售；最终成交会取消其他待处理申请；双方任一方可取消尚未完成交易。后续如调整规则，应同时修改实现、测试及接口契约。确认状态与真实环境验收统一记录在[联调验收清单](06-联调验收清单.md)。

## 验收

运行 `mvn "-Dtest=MarketplaceTests,ImageUploadTests" test`。测试覆盖搜索与分类、上下架、价格及图片地址校验、跨用户权限、多个买家申请、双确认完成、取消恢复、价格快照、并发接受及并发确认、注销账号状态与商品清理，以及图片上传、公开读取、商品保存、来源检查、无效文件与超限拒绝。

真实 MySQL 的并发重复申请回归测试使用 `mvn "-Dtest=ManualMarketplaceTests" "-Ddb.test.enabled=true" test`。测试显式在两个 REPEATABLE READ 事务中先建立旧快照，再同时申请，验证加锁后的当前读只能产生一条待处理申请。测试只创建独立随机标记的数据，并按本次编号及精确邮箱清理，不清空业务表。

建表文件为 `sql/04_marketplace.sql`，应在用户表创建后执行。已有旧版本表结构需要执行 `sql/06_marketplace_visibility.sql` 更新商品状态检查约束；启动还需完成角色、会话版本及其他迁移，完整顺序见 [README](../README.md)。测试使用独立 H2 数据源，真实 MySQL 并发回归和完整联调按[验收清单](06-联调验收清单.md)单独记录，不因测试命令存在而视为已通过。
