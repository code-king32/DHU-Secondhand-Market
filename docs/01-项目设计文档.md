## 1. 项目概述

### 1.1 项目名称
DHU Secondhand Market（DHU 校园二手交易平台 / 二手闲置交易系统）

### 1.2 项目背景与目标
面向校园学生的二手闲置物品交易平台，解决学生之间闲置物品流通问题。用户可注册登录后发布、浏览、购买二手商品，完成交易闭环。

**目标**：交付一个可运行、可演示的 Web 系统，并通过本项目完整实践软件工程流程（需求 → 设计 → 开发 → 测试 → 部署）与三人团队协作。

### 1.3 项目范围
- **一期（必做）**：用户模块、商品模块、交易模块 —— 三大核心闭环
- **二期（加分）**：留言沟通、交易评价、后台管理

## 2. 技术栈

| 层 | 技术选型 | 选型理由 |
|----|----------|----------|
| 后端框架 | Spring Boot 3.2 + Spring MVC | 当前主流 Java Web 框架，生态成熟 |
| ORM | MyBatis-Plus 3.5 | 内置通用 CRUD，减少手写 SQL，新手友好 |
| 数据库 | MySQL 8.0 | 稳定、课程通用 |
| 缓存/消息 | Redis 7（缓存 + 延迟队列），可选 RocketMQ | 缓存热点、防超卖、订单超时取消（技术亮点） |
| 前端模板 | Thymeleaf + Bootstrap 5 | 服务端渲染，只写 HTML + 少量 JS，Web 新手学习成本最低 |
| 认证 | Session + 登录拦截器 | 逻辑直观易调试（可选升级 Spring Security） |
| 构建工具 | Maven 3.8+ | 依赖管理 |
| 开发工具 | IntelliJ IDEA、Git、Navicat/DBeaver、Postman | |
| 运行环境 | JDK 17 | Spring Boot 3 要求 17+ |

## 3. 整体架构设计

### 3.1 分层架构（单体应用）

```
浏览器 (Thymeleaf 页面)
        │  HTTP
        ▼
┌─────────────────────────────────┐
│  表现层 Controller                │  接收请求、参数校验、返回视图/JSON
├─────────────────────────────────┤
│  业务层 Service (+ impl)         │  业务逻辑、事务
├─────────────────────────────────┤
│  持久层 Mapper (MyBatis-Plus)    │  数据访问
├─────────────────────────────────┤
│  MySQL 数据库                     │
└─────────────────────────────────┘
```

依赖方向：Controller → Service → Mapper → DB，**只允许上层依赖下层，禁止反向依赖**。

### 3.2 包结构（统一约定）

```
com.campus.secondhand
├── controller          # 控制器
├── service             # 业务接口
│   └── impl            # 业务实现
├── mapper              # MyBatis-Plus Mapper
├── entity              # 数据库实体类（对应表）
├── dto                 # 请求/传输对象
├── vo                  # 视图对象（返回给前端）
├── config              # 配置类（拦截器、静态资源等）
├── interceptor         # 登录拦截器
├── common              # 统一返回 Result、全局异常处理、常量
└── util                # 工具类
```

### 3.3 统一规范（vibe coding 的「公共地基」，必须人人遵守）

**统一返回格式**（所有接口 / 异步请求统一）：

```json
{
  "code": 200,        // 200 成功；400 参数错误；401 未登录；500 系统错误
  "msg": "success",
  "data": { }          // 业务数据，可为 null
}
```

**统一异常处理**：`@RestControllerAdvice` 全局捕获，业务异常抛自定义 `BizException`。

**命名规范**：
- 表名：小写蛇形，如 `goods`、`order_info`、`goods_image`
- 实体类：驼峰，对应表；Mapper：`XxxMapper`；Service：`XxxService` + `XxxServiceImpl`
- Controller 接口路径：`/模块/动作`，如 `/goods/list`、`/order/create`

## 4. 功能模块

### 4.1 模块总览与归属

| 模块 | 功能点 | 优先级 | 负责人 |
|------|--------|--------|--------|
| 用户模块 | 注册、登录/退出、个人资料、修改密码、个人主页 | 必做 | **A** |
| 商品模块 | 发布/编辑/下架/删除、图片上传、分类、搜索、分页列表、详情、收藏 | 必做 | **B** |
| 交易模块 | 下单、订单状态流转、我的买入/卖出、取消订单 | 必做 | **C** |
| 评价/留言 | 交易后互评、商品留言 | 加分 | **C** |
| 后台管理 | 管理员登录、用户管理、商品审核/下架 | 加分 | 后期再定 |

### 4.2 各模块功能点明细

**用户模块（A）**
- 注册：用户名唯一校验、密码加密（BCrypt）
- 登录/退出：Session 登录态、登录拦截器保护受限页面
- 个人资料：昵称、头像、联系方式、学校
- 个人主页：展示该用户发布的商品、历史评价

**商品模块（B）**
- 发布/编辑/下架/删除：标题、描述、价格、原价、分类、图片（多图）
- 图片上传：本地磁盘存储，返回访问 URL
- 分类与搜索：按分类筛选、关键词搜索、分页
- 详情页：图片轮播、卖家信息、浏览数
- 收藏：收藏/取消、我的收藏列表

**交易模块（C）**
- 下单：买家对在售商品下单，生成订单
- 订单状态机：`待付款 → 待发货 → 待收货 → 已完成`（可中途取消）
- 我的买入 / 我的卖出：分别以买家、卖家视角查看订单
- 取消订单：未发货前可取消，商品回到「在售」

**评价/留言（C，加分）**
- 交易完成后买卖双方互评（评分 + 文字）
- 商品留言区

**后台管理（加分）**
- 管理员登录、用户封禁、商品违规下架

### 4.3 技术亮点（简历加分项）

> 纯 CRUD 对简历无帮助。以下三个技术亮点让项目有深度，每人认领一个，答辩和简历都能讲。作为**进阶目标**，在一期核心跑通后逐步加入，不阻塞主线。

| 亮点 | 场景 | 技术方案 | 负责人 |
|------|------|----------|--------|
| Redis 缓存 | 商品详情 / 首页热点数据 | 缓存热点数据，处理缓存穿透（空值缓存）、缓存击穿（互斥锁）、缓存雪崩（过期时间打散） | **A** |
| 搜索 + 图片 | 关键词搜索、图片上传 | MySQL 全文索引（或 ES）、图片本地/OSS 存储、慢查询与索引优化 | **B** |
| 防超卖 + 超时取消 | 多人抢同一件商品、订单超时 | 乐观锁 + Redis 原子操作保证一件商品只成交一次；订单超时用延迟队列自动取消 | **C** |

## 5. 数据库设计

### 5.1 表清单

| 表名 | 说明 | 负责人 |
|------|------|--------|
| `user` | 用户表 | A |
| `category` | 商品分类表 | A（基础数据） |
| `goods` | 商品表 | B |
| `goods_image` | 商品图片表 | B |
| `order_info` | 订单表 | C |
| `favorite` | 收藏表 | B |
| `comment` | 留言/评价表 | C |

### 5.2 关键字段（建表时以此为准）

**user**：`id`、`username`、`password`、`nickname`、`avatar`、`phone`、`school`、`role`(USER/ADMIN)、`status`、`create_time`、`update_time`

**category**：`id`、`name`、`sort`

**goods**：`id`、`user_id`(发布者)、`category_id`、`title`、`description`、`price`、`original_price`、`status`(0在售/1已下架/2已售出)、`cover_img`、`view_count`、`create_time`、`update_time`

**goods_image**：`id`、`goods_id`、`url`

**order_info**：`id`、`order_no`、`goods_id`、`buyer_id`、`seller_id`、`price`、`status`(0待付款/1待发货/2待收货/3已完成/4已取消)、`create_time`、`pay_time`、`finish_time`

**favorite**：`id`、`user_id`、`goods_id`、`create_time`

**comment**：`id`、`goods_id`、`order_id`、`user_id`、`to_user_id`、`content`、`rating`、`create_time`

> 说明：管理员不单建表，用 `user.role` 区分。完整建表 SQL 在第 2 周由 A 落地。

## 6. 接口契约（概要）

- 统一前缀：无（REST 风格，按模块分组）
- 统一返回：上文 `Result{code, msg, data}`
- 登录态：Cookie 携带 `JSESSIONID`，受限接口由拦截器校验

**接口清单（概要，完整契约文档第 2 周补全）**

| 模块 | 关键接口示例 |
|------|-------------|
| 用户 | `POST /user/register`、`POST /user/login`、`GET /user/profile`、`POST /user/logout` |
| 商品 | `POST /goods/publish`、`GET /goods/list`、`GET /goods/detail/{id}`、`POST /goods/favorite` |
| 交易 | `POST /order/create`、`GET /order/my-buy`、`GET /order/my-sell`、`POST /order/confirm`、`POST /order/cancel` |

> ⚠️ 所有模块开发前，接口路径、请求参数、响应字段**必须先在本文档的接口契约里定死**，三人照此开发，避免联调返工。

## 7. 三人分工

> 原则：**按业务模块分，不按技术层分**。每人端到端负责自己模块（后端逻辑 + 对应页面），可独立跑通、不互相阻塞。

| 成员 | 角色 | 负责模块 | 具体任务 | 兼管 |
|------|------|----------|----------|------|
| **A（组长）** | 工程基础 + 用户模块 | 用户模块 | 项目骨架搭建、数据库建表落地、统一返回/异常、注册/登录/退出、个人资料、个人主页；**Redis 缓存（穿透/击穿/雪崩）** | Git 仓库、部署、文档 |
| **B** | 商品模块 | 商品模块 | 发布/编辑/下架/删除、图片上传、分类、搜索、分页、详情、收藏；**关键词搜索（全文索引）、慢查询优化** | |
| **C** | 交易模块 + 评价 | 交易模块 | 下单、订单状态机、我的买入/卖出、取消订单、评价/留言；**抢购防超卖（乐观锁/Redis 原子）、订单超时取消（延迟队列）** | 前端页面风格统一 |

**前端页面分工**：三人各自写自己模块的 Thymeleaf 页面，A 先提供公共模板页（页头/页脚/导航），C 负责最终统一样式。

### 依赖与协作关系

```
第1周：三人共同完成需求与设计（本文档）—— 数据库表结构 + 接口契约必须一起定死
第2-4周：A 先搭骨架 + 建表 + 用户模块（B、C 的前置）
第5-9周：B 商品模块、C 交易模块 并行开发
第10-12周：联调、统一样式、修 bug
第13-15周：测试、部署、文档、演示准备
```

**关键协作点**：
1. 数据库表结构 + 接口契约 = 三人的公共依赖，第 1 周定死，中途改动必须三人同步。
2. 谁负责哪个模块，谁就负责**把它跑通并验证**（vibe coding 下验证比生成更重要）。
3. 每个人的代码需能被自己**读懂并讲清逻辑**（答辩要求）。

## 9. 协作规范

- **Git**：`main` 主分支；每人一个功能分支（如 `feature/user`、`feature/goods`、`feature/order`），合并前互相 review。
- **提交信息**：`feat: 用户注册接口`、`fix: 修复订单状态流转 bug` 等。
- **公共模板页**：A 在第 2 周提供，所有人复用，避免样式各自为政。
- **统一返回/异常**：见 3.3 节，任何接口不得绕过。
- **图片存储**：先存本地磁盘（`/uploads/`），二期再考虑 OSS。
