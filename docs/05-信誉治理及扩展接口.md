# 信誉治理及扩展接口

本文件记录信誉评价、举报申诉、收藏和求购接口。写入操作要求已登录、校园邮箱已认证且账号正常；管理员接口还要求数据库中的 `role` 为 `ADMIN`。账号角色由部署维护人员设置，客户端不能注册或修改管理员角色。

以下流程属于当前实现选择：评分为1至5分，完成交易双方各评价一次；每个举报允许举报人申诉一次，申诉成立后重新打开原举报；管理员只允许正常、禁用两种账号状态切换，已注销账号不能恢复。这些参数和状态流程仍待团队确认，可在需求确认后调整；确认状态与真实环境验收见[联调验收清单](06-联调验收清单.md)。

## 公共约定

请求体使用 JSON，登录凭据使用 Session Cookie；浏览器凭据与来源配置见[身份认证与账号接口](02-身份认证接口.md)。分页参数为 `page` 和 `size`，默认第1页、每页20条，最多50条。分页响应结构为：

```json
{
  "items": [],
  "page": 1,
  "size": 20,
  "total": 0
}
```

输入去除前后空白，纯空白或不可见字符内容会被拒绝。接口不会返回邮箱密码、密码哈希或验证码。

## 交易评价

| 方法与路径 | 用途 |
|---|---|
| `POST /api/reviews` | 交易双方评价对方，成功201 |
| `GET /api/reviews?userId=1` | 公开查询某用户收到的评价 |
| `GET /api/users/{id}/reputation` | 公开信誉摘要，包含评价数与平均分 |

评价请求示例：

```json
{
  "tradeId": 1,
  "rating": 5,
  "comment": "沟通及时，物品符合描述"
}
```

服务端根据当前登录用户和交易双方计算被评价人，客户端不能自行指定被评价人。交易必须为 `COMPLETED`；每笔交易中每个参与人最多提交一条评价。非参与人403，未完成交易或重复评价409。评价内容最多1000字符。

评价响应包含 `id`、`tradeId`、`reviewerId`、`revieweeId`、`rating`、`comment`、`createdAt`。信誉摘要包含 `userId`、`reviewCount`、`averageRating`，没有评价时平均分为0。

## 举报与申诉

| 方法与路径 | 权限与用途 |
|---|---|
| `POST /api/reports` | 登录用户举报，成功201 |
| `GET /api/reports/mine` | 查询当前用户自己的举报 |
| `POST /api/reports/{id}/appeals` | 原举报处理后，举报人提交一次申诉，成功201 |
| `GET /api/reports/{id}/appeals` | 举报人查看自己的申诉 |
| `GET /api/admin/reports?status=OPEN` | 管理员分页查询举报，可省略状态 |
| `PUT /api/admin/reports/{id}/resolution` | 管理员处理待处理举报 |
| `GET /api/admin/appeals?status=OPEN` | 管理员分页查询申诉，可省略状态 |
| `PUT /api/admin/appeals/{id}/resolution` | 管理员处理申诉 |
| `GET /api/admin/reports/{id}/audit` | 管理员查询该举报的处理审计 |

举报请求：

```json
{
  "targetType": "GOODS",
  "targetId": 1,
  "reason": "商品描述疑似不实，请核查"
}
```

`targetType` 可为 `GOODS`、`USER`、`REVIEW`。服务端确认目标存在；不能举报自己的账号或内容；同一个用户对同一目标已有待处理举报时不重复创建。理由最多1000字符。

举报初始为 `OPEN`，管理员处理请求：

```json
{
  "decision": "RESOLVED",
  "note": "已核实并下架",
  "action": "HIDE_GOODS"
}
```

`decision` 为 `RESOLVED` 或 `REJECTED`。`action` 可省略或为 `NONE`，也可以选择：

- `HIDE_GOODS`：仅适用于商品举报，将商品设为独立的 `HIDDEN` 状态，卖家不能自行重新上架；交易中商品返回409，避免破坏已接受交易。
- `DISABLE_USER`：仅适用于用户举报，禁用被举报账号；不能作用于管理员自身、其他管理员或已注销账号。

驳回举报时只能使用 `NONE`。已处理举报不能再次直接处理。

举报人申诉请求：

```json
{
  "reason": "补充证据，请求重新核查"
}
```

原举报必须已处理，每个举报只接收一次申诉。管理员处理申诉请求：

```json
{
  "decision": "UPHELD",
  "note": "补充证据有效，重新核查"
}
```

申诉结果为 `UPHELD` 或 `REJECTED`。成立时原举报重置为 `OPEN` 并清除上次处理结果，等待管理员重新处理；不会自动恢复商品或账号。驳回则维持原举报状态。每次创建和处理均写入审计，保留前次处理信息。

举报响应字段为 `id`、`reporterId`、`targetType`、`targetId`、`reason`、`status`、`resolution`、`resolverId`、`createdAt`、`updatedAt`。申诉响应字段为 `id`、`reportId`、`appellantId`、`reason`、`status`、`resolution`、`resolverId`、`createdAt`、`updatedAt`。

## 账号状态管理

`PUT /api/admin/users/{id}/status`

```json
{
  "status": 0
}
```

仅管理员可调用，0表示正常、1表示禁用。不能修改自己或其他管理员账号，已注销账号不能恢复。禁用和恢复均记录管理员、目标、时间及新状态，并递增会话版本；旧会话即使在账号恢复后也不能继续使用，需要重新登录。

## 收藏

| 方法与路径 | 用途 |
|---|---|
| `PUT /api/favorites/{goodsId}` | 收藏在售商品，重复调用保持一条记录 |
| `DELETE /api/favorites/{goodsId}` | 取消收藏，返回204，重复调用仍成功 |
| `GET /api/favorites` | 分页查询自己的收藏 |

收藏只能由当前用户读取和修改。添加时商品必须处于 `ON_SALE`，卖家账号正常且已认证；之后商品变为已售或自行下架时，既有收藏列表显示其最新状态。管理员隐藏的 `HIDDEN` 商品和账号不可用卖家的商品从收藏列表和计数中排除。响应包含收藏编号、商品编号、标题、价格、状态和收藏时间。

## 求购与教材专区

| 方法与路径 | 用途 |
|---|---|
| `POST /api/wanted` | 发布求购，成功201 |
| `GET /api/wanted?q=教材&category=TEXTBOOK` | 公开分页检索有效求购 |
| `PUT /api/wanted/{id}/close` | 发布人关闭求购，重复关闭保持成功 |

发布请求：

```json
{
  "title": "求购高等数学教材",
  "description": "版本不限，希望保留完整页面",
  "maxPrice": 30.00,
  "category": "TEXTBOOK"
}
```

标题最多100字符，说明最多2000字符，预算范围为0至9999999.99，最多两位小数。分类为 `TEXTBOOK`、`ELECTRONICS`、`DAILY`、`CLOTHING`、`OTHER`，省略时为 `OTHER`。公开检索只返回 `OPEN` 且发布人账号正常、已认证的求购；关键词中的通配符按普通文字处理。关闭只能由本人执行。响应包含 `id`、`userId`、`title`、`description`、`maxPrice`、`category`、`status` 和创建、更新时间。

教材商品专区直接使用商品接口的 `category=TEXTBOOK` 筛选；教材求购使用上面的求购筛选，复用商品和求购模块。

## 数据库与验收

先执行账号角色迁移和商品交易建表脚本，再执行 `sql/05_community.sql`；启动前还需完成商品治理状态及会话版本等后续迁移。举报申诉审计和账号状态审计独立保存，评价、收藏使用唯一约束阻止重复。

所有写入事务重新锁定并校验操作者账号状态，避免控制器会话检查后账号被注销仍继续写入。涉及两个用户时按编号升序锁定，评价与申诉还锁定对应交易或举报，使重复提交和状态流转串行处理。
